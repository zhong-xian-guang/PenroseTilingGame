# 15: 大鋪砌效能

**What to build:** 鋪砌長到數千片時，平移、縮放和放置仍然流暢。已確認鋪砌畫進離屏快取的圖塊，只重畫預放、預覽和疊加層；規則引擎用空間索引，每次放置只重算受影響區域的候選放置與死局判定。

**Blocked by:** 05 成長圓

**Status:** resolved

- [x] 已確認鋪砌畫進離屏快取的圖塊，視窗外的部分不繪製
- [x] 引擎以空間索引查詢鄰近拼塊；每次放置只重算局部，查詢結果與全盤重算一致（有測試）
- [x] 在中階手機上，鋪砌 5000 片時平移與縮放維持接近 60fps（實機量測，見 Comments）
- [x] 每次放置後，引擎的處理時間在中階手機上低於一幀（只有載入後的第一次放置，因 JIT 尚未暖機，約 17–20 ms，見 Comments）

## 實作紀錄

- 引擎（`src/engine/tiling.ts`）：拼塊依中心點放進均勻網格，重疊檢查只看附近 3×3 格，並先用浮點外框（保守餘量）剔除。
  每條邊界邊快取「可貼上的合法放置」；放置後只重查附近（INVALIDATE_RADIUS）仍合法的選項（加拼塊只會讓合法性更嚴），
  拿掉拼塊則重建附近項目。邊界邊集合增量維護，候選順序與原本全盤掃描完全相同。
  `game.ts`：成長圓的鞋帶公式累加改為增量（加總順序不變，結果逐位元相同），`tiles()`/`confirmedTiles()` 快照只在棋盤改變時重建。
  公開 API 不變。
- 測試：`tests/engine/incremental.test.ts` 把增量結果（候選、死局）釘在「同樣拼塊重新建局」的全盤重算上，含轉向與移除；
  把 INVALIDATE_RADIUS 故意縮小會讓它失敗（已驗證）。
- 繪製（`src/board/tile-layer.ts`）：已確認鋪砌畫進 256 裝置像素的離屏圖塊，只畫視窗內的圖塊；新確認的拼塊直接疊畫進已快取的圖塊。
  縮放時先拉伸舊圖塊，停止 150ms 或偏離超過 2 倍時以新比例分批重建（每幀 6ms 預算，未完成處由舊一代墊底），不會卡住一幀。
  預放、預覽、死局、成長圓每幀重畫。

## Comments

**實機量測（2026-10-24）**：ASUS ZenFone 5Z，Snapdragon 845（2018 年旗艦，以今天來看約為中階），Android 10，Chrome 147，
viewport 375×647 CSS px、DPR 2.875（畫布 1080×1860 裝置 px）。手機在充電，電池 35 °C。

量測工具：`bench.html`（`src/bench/main.ts`）是獨立的量測頁。它取 deflate 8 次的太陽中最靠近中心的 5000 片，用真正的 `Board` 與 `TileLayer` 顯示，
不碰自動存檔與 IndexedDB。流程：平移 10 s（前 5 s 看得到整個鋪砌，後 5 s 放大到開局的比例），縮放 10 s（在「整個鋪砌」與它的 4 倍之間來回），
然後每幀放一片同一個鋪砌中的下一片，共 50 片，並計時引擎。結果寫到 `window.__bench`。
只有 `npm run build:bench`（輸出 `dist-bench/`，沒有 service worker）與 dev server 會產生它，production build 不含。
用 `npm run device:perf` 透過 CDP 讀取結果。

建局：參考鋪砌 113 ms；`createGame` 加第一次查詢 120–128 ms。

畫面（3 次，每次 50 片放置）：

| | fps | 幀中位數 | 幀 p95 | 最慢一幀 |
|---|---|---|---|---|
| 平移（整個鋪砌） | 59.85 | 16.7 ms | 16.8–17.0 ms | 17.0–17.7 ms |
| 平移（放大） | 59.85 | 16.7 ms | 16.8–17.0 ms | 16.9–17.4 ms |
| 縮放 | 58.9–59.4 | 16.7 ms | 16.9 ms | 33.6–66.9 ms（偶爾掉 1–3 幀，發生在新比例的圖塊重建時） |
| 放置期間 | 57.5–58.7 | 16.7 ms | 16.9–17.1 ms | 33.4–49.9 ms |

引擎，每次放置（`place()` 本身／再加上兩種候選、死局、成長圓、確認拼塊、分數的查詢）：

| | 中位數 | p90 | 最大 |
|---|---|---|---|
| `place()`（3 次 × 50 片） | 2.8–3.0 ms | 5.0–6.3 ms | 9.9–19.5 ms |
| `place()` + 查詢 | 4.9–5.1 ms | 8.6–10.2 ms | 26.5–39.4 ms |
| `place()`（2 次 × 200 片） | 2.7–2.8 ms | 5.3–5.5 ms | 17.4 ms（第 1 片）／7.2 ms |
| `place()` + 查詢（200 片） | 4.5–4.6 ms | 9.2 ms | 34.8 ms（第 1 片）／12.5 ms |

最慢的一次放置是頁面載入後的第一次，這時 JIT 還沒暖機。200 片那組，第一次跑：`place()` 只有第 1 片超過 16.7 ms；加上全部查詢的話是 2 片（第 1 片與另 1 片，可能是 GC）。
第二次跑（已暖機）：400 次量測都沒有超過，`place()` 最多 7.2 ms，加上全部查詢最多 12.5 ms。
50 片那三次的最大值（9.9–19.5 ms）沒有記錄是第幾片；量測工具在那之後才加上 `maxAt` 與 `over16ms`。
結論：除了暖機前的頭一兩次之外，放置都在一幀內，因此勾選第 4 項，並在項目上註明這個例外。
